# Android Home-Screen Widget Contract

## Scenario: showing the next class on the Android launcher

### 1. Scope / Trigger

Use this contract when changing the Android App Widget, the `WidgetSnapshot` Capacitor bridge, the Web-side snapshot builder, the widget refresh scheduling, or anything that reads/writes the snapshot preference file. The widget is Android-only; browser/PWA and the native import shell must stay untouched and unaffected.

The core constraint that shapes everything here: **course data lives only in the WebView's `localStorage`** (Zustand persist, key `class-track-storage`). A widget runs in the app's own process and cannot read WebView storage, so a one-way snapshot channel is the only data path. The Web layer is the single source of truth for every calendar and timezone computation; native only compares `long` epochs and renders.

### 2. Signatures

Web → native boundary, registered as `WidgetSnapshot`:

```ts
interface WidgetSnapshotPlugin {
  pushSnapshot(options: { snapshotJson: string }): Promise<void>
  consumePendingRoute(): Promise<{ route: string | null }>
  getExactAlarmStatus(): Promise<{ available: boolean; exact: boolean }>
  requestExactAlarmPermission(): Promise<{ launched: boolean; exact: boolean }>
  requestPinWidget(options: { preset: WidgetPresetId }): Promise<{ supported: boolean; requested: boolean }>
  getPinCapability(): Promise<WidgetPinCapability>
  consumePinObservation(): Promise<WidgetPinObservation>
  openPinShortcutPermissionSettings(): Promise<PinNavigationResult>
  openWidgetGallery(): Promise<PinNavigationResult>
  addListener(eventName: 'resumed', listenerFunc: () => void): Promise<PluginListenerHandle>
}

function isNativeWidgetSnapshotAvailable(): boolean // android && plugin registered
```

The frozen cross-layer payload (Web builds it, native consumes it):

```ts
type WidgetSnapshotV1 = {
  schemaVersion: 1
  status: 'ok' | 'empty' | 'unavailable'
  generatedAtEpochMs: number
  validUntilEpochMs: number
  entries: WidgetOccurrence[]   // ascending by startEpochMs, max 800
  dayEndEpochMs: number[]       // index = dayOffset, value = local 24:00 of that day
  generatedAt: string           // diagnostic only
  timezone: string              // diagnostic only
}

type WidgetOccurrence = {
  id: string        // `${class.id}#${dayKey}`
  name: string
  classroom: string
  sections: string  // "3-4" or "3"
  startEpochMs: number
  endEpochMs: number
  startLabel: string // "10:00", pre-formatted by Web
  endLabel: string
  dayKey: string     // "2026-09-19"
  dayOffset: number  // 0 = the day the snapshot was generated
  weekdayLabel: string
}
```

Native surface that future work must reuse rather than re-derive:

```java
// all refresh paths converge here; it is idempotent
WidgetRefreshController.refresh(context, trigger)      // render + reschedule
WidgetRefreshController.rescheduleOnly(context, trigger) // reschedule only (receiver.onUpdate)

// the ONLY Java -> Kotlin call site in this feature
WidgetRefreshBridge.requestRefresh(context)

WidgetDisplayState.Type = { MISSING, UNAVAILABLE, EMPTY, STALE, NO_UPCOMING, READY }
WidgetStateResolver.resolve(WidgetSnapshot, nowEpochMs)
```

### 3. Contracts

- **Storage**: `SharedPreferences("class-track-widget", MODE_PRIVATE)`, single key `snapshot_json`, written with one `commit()`. One key means a reader can never observe a half-updated snapshot. `apply()` must not be used: the plugin may only `resolve()` after confirming the write landed.
- **Bounded payload**: 256 KiB and ≤ 800 entries. The Web side measures UTF-8 bytes via `TextEncoder` (not `String.length`, which under-counts Chinese by 2×) and skips the push rather than sending a payload native will reject.
- **Coverage window**: from the generation day to the last day of the semester's last week, clamped to at least the generation day, capped at 400 days and 800 entries. When the entry cap truncates the window, `validUntilEpochMs` and `dayEndEpochMs` shrink with it — a day must never be listed as covered while its courses were dropped, or the widget would silently render "no class today".
- **`dayEndEpochMs[dayOffset]` is the only way native determines "what day is it"**. This removes all date/timezone math from native: no `java.time`, no `Calendar`, no `SimpleDateFormat`, no desugaring.
- **The snapshot also carries today's date label, as an optional field pair** (added 2026-09-23): Web adds `todayDayKey` (`YYYY-MM-DD`) + `todayWeekdayLabel` (`周X`), pre-formatted from the same `now` it already uses, to **all three** `status` values. Native needs them because "today has no class" means `entries` holds nothing for today, so the hero's date line has no other source — and native must not start doing date math (`dayEndEpochMs` stays the only "what day is it" mechanism). They are **optional**: `WidgetSnapshotParser` reads them with `optString(key, "")`, `schemaVersion` stays `1`, and an old stored snapshot renders without the date line instead of degrading to "please sync".
- **`status` distinguishes three kinds of "nothing to show"**: `empty` (no courses imported), `unavailable` (no `firstWeekStartDate`, so dates cannot be derived — never guess "week N + today"), `ok`. `schemaVersion` mismatch is treated as no snapshot; the stored file is kept, nothing throws.
- **Hero selection is `endEpochMs > now`, never `startEpochMs > now`.** A class that already started but has not ended is still the hero (labelled "in progress"). Only when no entry has `endEpochMs > now` may the widget show "no class".
- **The hero slot never shows another day's class** (added 2026-09-23, product-owner requirement): when today has no class left — it never had one (weekend/holiday) or every class is finished — the hero line becomes `WidgetBodyLine.Kind.HERO_EMPTY` instead of `HERO`, i.e. three rows: today's date (caption, accent; the 「样式」 entry stays on that row **except** in `compact`, whose counter row already carries one) → 「今天无课」 / 「今天已无课」 (title, produced by `todayEmptyText`, the same function the summary/counter rows use) → one light line (body) whose copy is **tiered by style, never by size**: wide (`next_up`) 「享受你的美好时光吧」 / 「今天的课上完啦，好好休息」, narrow (`compact`) 「放松一下吧」 / 「课上完啦」. The trigger is `state.heroState == UPCOMING_OTHER_DAY` (equivalently `hero.dayOffset != currentDayOffset`), handed to `WidgetLinePolicy.resolve(config, plan, heroIsToday, dualColumn)` as `heroIsToday` — **no new time comparison anywhere**. Three consequences are load-bearing: (a) `next_up` / `compact` must then add the `NEXT_OTHER` line whenever `plan.getSource() != TOMORROW` (`day_list` keeps its old "has rows" rule), otherwise a 「今天已上完」 card loses the only hint about when the next class is; (b) `compact`'s follow-up rows start at the first **not-finished** row instead of `firstRowAfterHero` — there is no hero left to skip, and skipping anyway silently swallowed tomorrow's first class — while finished rows still never appear there; (c) `widget_hero_upcoming_other_day` was deleted (runtime can no longer produce it), the two-column left card centres those three lines and drops the course name / time · room / 「今天还有 N 节」, and **both** height estimators (`bodyTextLines`, `headerTextLines`) must carry the same three-line shape (caption + title + body) or the fill plan inflates the fonts.
- **`READY` vs `NO_UPCOMING` vs `EMPTY` must stay distinct**: a valid snapshot with no unfinished course means "the semester is over", which is a different message from "no timetable data". Merging them makes the widget tell users their data is missing when the term simply ended.
- **Five-tier refresh ladder**, all converging on one idempotent path:
  - **L1** plugin push (immediate render + a 0-delay unique Work as a persisted fallback).
  - **L2** `ACTION_DATE_CHANGED` / `ACTION_TIME_SET` / `ACTION_TIMEZONE_CHANGED` declared on a manifest receiver. These are on Android 8+ implicit-broadcast exception list, so they are delivered regardless of `targetSdk`; midnight and time changes are corrected exactly, with zero permissions.
  - **L3** `AlarmManager.setExactAndAllowWhileIdle`, gated behind `canScheduleExactAlarms()`. This is the **user-optional** tier: `SCHEDULE_EXACT_ALARM` is a special app access that Android 14+ denies by default. Without it the widget silently falls back to L4 — never crash, never show an error. Do not declare `USE_EXACT_ALARM` (that one is auto-granted and reserved for alarm/calendar apps).
  - **L4** `OneTimeWorkRequest` with `setInitialDelay(nextBoundary - now)`, `ExistingWorkPolicy.REPLACE`, unique name `widget-boundary-refresh`.
  - **L5** `appwidget-provider` `updatePeriodMillis="1800000"` (the AOSP `MIN_UPDATE_PERIOD` floor). Delivered by the system's own alarm, independent of WorkManager and of whether our process was pre-warmed. **Never set it to 0.**
- **Do not add a `PeriodicWorkRequest`**: L5 is the more independent, cheaper periodic path. Do not add a `BOOT_COMPLETED` receiver either: WorkManager reschedules its own work after reboot. Note that `RECEIVE_BOOT_COMPLETED`, `WAKE_LOCK`, `FOREGROUND_SERVICE` and `ACCESS_NETWORK_STATE` appear in the merged manifest from `androidx.work`'s library manifest — that is a merge fact, not a declaration of ours. L3 alarms do **not** survive reboot, which is a documented limitation, not a bug.
- **Java ↔ Kotlin boundary is exactly one call**: `WidgetRefreshBridge.requestRefresh(Context)`. The Capacitor plugin stays Java (same shape as `CourseImportPlugin`); Glance must be Kotlin. Keep the surface at "one static method, one Context argument, no return value".
- **Privacy**: the snapshot carries only what is displayed. Teacher, `courseId`, `classId`, notes, URLs and cookies must never cross the bridge. Diagnostics use one tag (`ClassTrack.Widget`) and emit only a phase, a byte length, and whitelisted enum values — never a course name, classroom, time, or payload text.
- **`initialLayout` must use only RemoteViews-allowed classes.** The `appwidget-provider` `initialLayout` is inflated by the *host* as a legacy RemoteViews layout, so it accepts only annotated classes (`FrameLayout`, `LinearLayout`, `TextView`, `ImageView`, ...). A bare `<View>` throws `InflateException: Class not allowed to be inflated android.view.View` and the launcher renders "Can't load widget". Keep it to a single background-carrying container with no children.
- **Never call `goAsync()` from `AppWidgetProvider` callbacks.** In `onUpdate` / `onEnabled` / `onAppWidgetOptionsChanged` it can return `null`; calling `pending.finish()` then throws an NPE that kills the process — and a process killed mid-update leaves the widget stuck on `initialLayout`, i.e. a blank card. Those callbacks only need to keep the boundary chain alive, so enqueue durable WorkManager work instead. In a real `onReceive`, `goAsync()` is valid but must still be null-checked.
- **The widget's click route must be a route that actually exists.** The schedule page is the *index* route (`/`), not `/schedule`. A route that matches nothing makes React Router render `root.tsx`'s `ErrorBoundary`, which **replaces the whole component tree and unmounts the snapshot-sync component** — so a bad click route also silently stops sync. Guard the constant with a `matchRoutes(routes, ROUTE)` test, the same pattern as `native-shell-url.test.ts`.
- **Widget click**: starts `MainActivity` with extra `classtrack_widget_route`. The route is whitelisted to the compile-time constant `/` (`WidgetPendingRoute.ROUTE_SCHEDULE`, the *index* route — see the guard bullet above), so a foreign app cannot inject an arbitrary path into client-side navigation, and the Intent carries no course data.
- **Per-instance style config** (added 2026-09-19 requirement change): layout style (`day_list` / `next_up` / `compact`) and finished-class policy (`show_dim` / `hide` / `collapse`) are stored **per widget instance** in the Glance state container (`updateAppWidgetState` / `getAppWidgetState` + `PreferencesGlanceStateDefinition`, keys `layout_style` / `finished_policy`). Unknown or corrupt values fall back to the defaults (`WidgetStyleConfig.DEFAULT_LAYOUT_STYLE` / `DEFAULT_FINISHED_POLICY`, currently `next_up` + `show_dim`); never throw, never blank the widget. The default layout style is **「接下来」(next_up)** because it answers both 「现在上什么」 and 「今天还有什么」 without the user having to configure anything at placement time (changed 2026-09-20 from `day_list`, per the product owner). A third per-instance group, **大格子表现** (`wide_layout`: `adaptive` / `dense` / `two_column`, `WidgetStyleConfig.WideLayout`, added 2026-09-20), follows the same read/fallback/write/clear path: `adaptive` (default) follows the size, `dense` additionally shows section numbers and today's counts, `two_column` splits the body when the geometry allows it. `WidgetStyleState.clear()` must delete all three keys — a reused `appWidgetId` would otherwise inherit a stale layout. The mapping is `GlanceAppWidgetManager.getAppWidgetId(glanceId)` / `getGlanceIdBy(appWidgetId)`. `onDeleted` clears the instance's keys so a reused `appWidgetId` cannot inherit a previous style.
- **In-app 「添加到桌面」 (added 2026-09-20, retargeted 2026-09-21)**: the schedule page's top bar carries a `CalendarPlus` icon button (rendered **only** when `isNativeWidgetSnapshotAvailable()` is true — in a browser there is no home screen to add to). It opens a `Sheet` listing `WIDGET_PIN_PRESETS` (`app/features/schedule/widgetPinPresets.ts`): **five presets named by cell**, each = **target cell + layout style + 大格子表现** (`cell_2x2` / `cell_2x3` / `cell_4x2` / `cell_4x3` / `cell_6x3`), with the honest note that the final size is decided by the launcher. The preset **ids must equal `WidgetPreset.java`'s whitelist** and each id must have a provider in `WidgetProviderRegistry.java` — native silently falls back to 「no preset」 on an unknown string, so `widgetPinPresets.test.ts` reads the real `WidgetProviderRegistry.java`, the five `res/xml/widget_info_*.xml` and `res/values/strings.xml` and fails on any drift. Native `requestPinWidget({preset})` validates the id (unknown → `INVALID_PAYLOAD`), checks `AppWidgetManager.isRequestPinAppWidgetSupported()`, resolves the **provider for that preset** (`WidgetProviders.rendererFor`), stores the pending preset, snapshots the pre-request instance ids (`WidgetPinBaseline`) and calls `requestPinAppWidget(provider, extras, successCallback)`. It resolves `{supported, requested}` — **no error codes**: unsupported and user-cancelled are normal outcomes the UI explains.
- **The pin size hint is smoke, not a contract** (device-measured 2026-09-20): `extras` carries `OPTION_APPWIDGET_MIN_WIDTH/HEIGHT` of the preset's target cell, but **AOSP Launcher3 ignored them** — the pin sheet labelled the widget 「4 × 3」 (the provider's `targetCellWidth/Height`) and placed a 4×3 instance for a 6×3 preset. So the copy promises only what we control: the style/表现 are applied, the size is "以桌面实际放下为准，可以自己拖动调整". Never word the UI as "will be placed at 6×3" until a specific launcher is measured to honour the hint. The picker's own size label is **not** fully ours either: emulator-measured (Launcher3, Android 16 image, 5-column phone grid) the entry for the `cell_6x3` provider — whose APK metadata really declares `targetCellWidth=6/Height=3`, verified with `aapt2 dump xmltree` — was labelled 「2 × 2」, i.e. the launcher clamps the displayed span to whatever fits its grid. So: declare the honest `targetCell*` per provider, render an honest `previewLayout`, and never promise a size in copy.
- **One single source for the「尺寸可以自己调」copy, and one entry into the panel** (added 2026-09-22): `WIDGET_PIN_SIZE_TUNING_HINT` (`app/features/schedule/widgetPinPresets.ts`) is the **only** place that sentence exists; it is rendered both inside the pin panel and inside the post-import guide, and `widgetPinPresets.test.ts` asserts the constant's content *and* that `WidgetPinEntry.tsx` references it by name — so a second hand-written sentence fails the suite (this covers the 「尺寸可调」 hint that the panel used to state only loosely in its description). The panel Sheet is now **controlled** (`open` / `onOpenChange` bound to `uiSlice.widgetPinSheetOpen`), so the pin UI stays a single implementation while other surfaces can open it. The post-import guide itself (`app/lib/widget-guide.ts` + `app/components/native-widget/WidgetGuideDialog.tsx`, mounted in `root.tsx`'s Layout next to `WidgetSnapshotSync`) is shown **only** when `isNativeWidgetSnapshotAvailable()` is true — on browser/PWA/iOS there is no home-screen widget, so pointing at one would be an empty promise. Its primary action closes the guide, navigates to the index route and sets `widgetPinSheetOpen`, and it must stay mounted in `root.tsx` (never inside `ImportDialog`, which unmounts the moment the import succeeds). The「already seen」flag lives in its own localStorage key (`class-track-widget-guide-seen`) and is deliberately **outside** the Zustand `partialize` whitelist: it is a per-device one-shot and must not travel with a backup to a new device. The guide is triggered from all three import success paths, and `app/lib/widget-guide.test.ts` guards that wiring by counting the call sites in the real source file.
- **A second one-shot guide follows the widget guide** (added 2026-09-23): 「去个人中心看看」. Copy/title/buttons live in `app/lib/profile-guide.ts`, the dialog is `ProfileGuideDialog` (mounted next to `WidgetGuideDialog` in `root.tsx`, `null` outside Android native, body exported separately for the static-render test), and it opens on `showProfileGuide && !widgetPinSheetOpen`. `WidgetGuideDialog`'s close handler — **both** buttons, since the requirement is 「第一段一关就接第二段」 regardless of whether a card was actually added — checks `shouldShowProfileGuide({nativeWidgetAvailable: true, seen: hasSeenProfileGuide()})`, writes its flag **at the moment it decides to show** (own device-local key `class-track-profile-guide-seen`, never in `partialize`), and flips `uiSlice.showProfileGuide`. Because the 「去添加」 path opens the pin sheet immediately, the second guide waits for `widgetPinSheetOpen` to fall rather than stacking on the panel — no extra "pending" flag is needed, the sheet's open state *is* the flag. 「前往」 closes and navigates to `/profile`; 「暂时不用」 only closes. The flag plumbing is shared with the widget guide through `app/lib/guide-storage.ts` (one read/write implementation for both one-shot guides), and `profile-guide.test.ts` guards the wiring by reading the real sources.
- **Only the system's confirmation callback means "added", and the id it carries is not trustworthy** (rewritten 2026-09-21 after device + emulator review; supersedes the 2026-09-20 render-side fallback): `requestPinAppWidget(provider, extras, successCallback)` **returns immediately** and its `true` only means "the request was accepted" — it is not placement, and a failed pin fires **no** callback at all. Device-measured on the target phone (PKR110 / ColorOS / Android 16): the launcher did start `AddItemActivity` (`CONFIRM_PIN_APPWIDGET`) but never brought it to the foreground (`mCurrentFocus` stayed on our Activity, and `dumpsys appwidget | grep -c classtrack` stayed at 1), while the panel had already shown 「✓ 已添加」 — i.e. the app lied to the user. The contract is therefore: (a) always pass a `successCallback` (`PendingIntent.getBroadcast`, `FLAG_IMMUTABLE`) targeting `WidgetPinResultReceiver`; (b) **only** that callback may be reported as success (`WidgetPinResult` one-shot slot + the `pin_confirmed` phase; web polls `consumePinResult()`); (c) resolve the target instance in **two tiers** (`WidgetPinTargets.resolve`, pinned by `WidgetPinTargetsTest`), because **the callback's `EXTRA_APPWIDGET_ID` is unreliable**: emulator-measured (AOSP Launcher3, Android 16 image) it is `0` while the real new instance was `8`, and a naive `getGlanceIdBy(0)` throws → the preset is silently dropped with no user-visible symptom (this cannot be caught on the target phone, where the launcher never confirms at all). Tier 1: use the callback id only if it is present in the provider's current id set. Tier 2: take the set difference between the ids captured **before** the request (`WidgetPinBaseline`, one-shot, 5-minute timeout, mirroring `WidgetPendingPreset`) and the ids after it. `null` baseline (never recorded / expired) must mean **"unknown"**, never "empty": treating it as empty makes the difference equal to *every* instance and the preset would be written onto the user's older cards. If neither tier resolves anything, write nothing and **do not consume** the preset slot (`pin_confirmed_unresolved`) — a launcher that opens the config page afterwards can still use it. Do **not** reintroduce "apply the pending preset to whichever instance looks new" (`WidgetPendingPreset.claim()` + `WidgetStyleState.isConfigured` were both deleted: the callback already brackets the request, and two concurrent renders could claim the same preset). `WidgetPinResultReceiver` is registered `exported="false"` — the broadcast arrives through our own `PendingIntent` (sent with our identity), so no export is needed (verified end-to-end on the emulator). It may use `goAsync()` (with a null check and `finish()` on every path): the "never `goAsync()`" rule above targets `AppWidgetProvider` callbacks, whose `pendingResult` can be null. `WidgetConfigActivity` keeps consuming the same slot for launchers that do open it, and whoever arrives first wins.
- **When the system silently swallows the pin, the copy must say so** (added 2026-09-21): some OEM launchers ignore the request outright, so after ~10 s without a callback the panel must state 「系统没有完成添加（部分厂商桌面会忽略这个请求）」 instead of implying failure-by-retry (retrying the same request fails the same way). The manual steps (long-press home → widgets → drag) are **always visible at the bottom of the panel**, not only on failure: on those launchers they are the only path that works. The in-between state is worded neutrally (「已请求系统添加…」) and must never contain 「已添加」; `'requested' === true` is never rendered as success.
- **Vendor diagnosis picks copy, never capability** (added 2026-09-21): `WidgetVendorFamily` classifies `Build.MANUFACTURER` / `Build.BRAND` into `XIAOMI` / `OPPO` / `VIVO` / `HONOR` / `OTHER` (wire names lowercase). `widgetPinPresets.test.ts` reads **both** that Java file and `app/lib/native-widget-snapshot.ts` and asserts the enum and the Web union type match member-for-member — a family added on one side only is a red test. `Mi` must match **exactly**: as a substring it also hits `Micromax` / `Microsoft`, which run near-AOSP launchers and would then be handed Xiaomi's guidance. `huawei` maps to `OTHER` **on purpose** — any Huawei device still reaching this code is pre-HarmonyOS EMUI, i.e. the 「legacy system」 bucket. Two hard rules: the family may only select copy and decide whether an entry point is shown, and **`HONOR` must keep all three capability switches `false`** (`WidgetVendorSupportTest#honorHasNoVendorSpecificCapabilityAtAll`) — Honor's own docs say it follows the plain Google widget spec, so it is allowed copy differences and nothing else. `WidgetVendorSupport.MODERN_SDK_FLOOR = 34`; below it every vendor-specific string must stay byte-identical to the generic one.
- **Capability comes from behaviour, in three stages — the third is the no-callback re-check** (added 2026-09-21): T0 `isRequestPinAppWidgetSupported()` only short-circuits the request (some ROMs return `true` unconditionally, so it is never a 「supported」 conclusion); T1 `PinAttempt.shouldFailFast` (~2 s, explicitly an inference); T2 `WidgetPinResult` (the only authoritative success); **T3** at the end of the wait window the panel calls `consumePinObservation()`, which re-runs the *existing* difference verdict — `WidgetPinTargets.resolve(WidgetPinBaseline.peek(now), WidgetProviders.allAppWidgetIds(ctx), -1)` — and answers `{observed, count}` (`WidgetPinObservation`: one-shot, 5-minute timeout, **numbers only, never ids**). It uses `peek` because `consume` would take the baseline away while the callback can still arrive *after* the re-check (that path needs the same baseline to compensate for `EXTRA_APPWIDGET_ID = 0`). Precedence: T2 wins outright; otherwise T3 overrides T1's 「系统没有弹出确认界面」. A `null` baseline (never recorded / expired) must never be read as 「no instances」. Since T3 can only prove 「桌面上多了一张卡片」 and not who put it there, its verdict is a **separate** `added_observed` whose copy carries the qualifier 「如果不是你刚添加的，请忽略。」, while callback-backed `added` stays silent. `WidgetPinResult.hasConfirmed(now)` is the read-only query that keeps 「callback path first」 without stealing the panel's result.
- **Vendor-specific manual steps, because each entry point has a different name and depth** (added 2026-09-21): the former single generic sentence pointed the wrong way on all four vendors, so `MANUAL_HINT_BY_FAMILY` now carries five entries — Xiaomi 「小部件」→ search → 「安卓小部件」, OPPO 「卡片」→ search for the app, vivo 「组件」→「应用挂件」, Honor 「服务卡片 / 桌面卡片」→「窗口小工具 / 经典小工具」, plus the generic 「小工具 / 小组件」 for `OTHER` and legacy systems. `manualSteps(family, sizeList = widgetPinSizeList())` appends the size list (generated from the preset table, never hand-written) and, for the four vendors only, the 「当前页放不下时，先滑到有空位的页面」 note (Honor/Huawei do not open a new page). Gates: the family keys must equal the native enum, every hint must contain its own key phrase, and the four vendor hints must carry the space note while `other` must not. `WIDGET_PIN_MANUAL_STEPS` was **deleted** — a leftover reference is now a compile error, which is the guard (no string search needed).
- **Vendor entry points are navigation only, and two of them sit behind a probe** (added 2026-09-21): Xiaomi adds `extras(addType="appWidgetDetail", widgetName="<pkg>/<FullProviderClass>")` **only when** `WidgetVendorProbe` reports that the device supports the widget-centre detail page (official `ContentResolver.call("content://com.miui.personalassistant.widget.external", "isMiuiWidgetDetailPageSupported", …)`), and the extras are *in addition to* the standard pin — callback, baseline and all three probe stages unchanged, so rolling back is one flag. Failure to probe (provider absent, exception, `null`, missing key) counts as 「not supported」 and is **not cached**; only a real answer is. vivo's 「打开组件库」 builds `vivo://com.bbk.launcher2/origin?pkg=…&classname=…&comType=0&locType=1` (permission `com.bbk.launcher2.permission.JUMP_ORIGIN`, declared for navigation only) from a single constructor, and the parameter name follows vivo's **code sample** (`comType`) even though its prose says `cmpType` — it is a named constant, so one edit fixes it if a device disagrees. OPPO gets **no button at all**: no zero-review in-app add path is documented for ColorOS, so it stays copy-only. Both navigations are fail-soft: unresolvable target or any `RuntimeException` from `startActivity` → `{launched:false, step:'none'}` plus one diagnostic line, never an error dialog, never a crash.
- **Open items from the vendor round (2026-09-21) — covered by unit tests only, no device available**: V1 Xiaomi's detail-page extras against an **unreviewed** native widget; V2 whether Honor really sends no callback; V3 the Xiaomi 「创建桌面快捷方式」 gate actually gating the pin; V4 the four vendors' real entry names on current builds; V5 the vivo gallery URI (and `comType` vs `cmpType`); V6 vivo's `requestPinAppWidget` behaviour for an unreviewed app. Recorded in `.trellis/tasks/09-21-widget-pin-vendor-probe/verification.md` with an explicit ⏳ for each — do not report any of them as verified without device evidence.
- **Seven providers, two maintained** (added 2026-09-21, **retargeted the same day**): `AndroidManifest.xml` declares seven `AppWidgetProvider` receivers — `ClassTrackWidgetReceiver` (**4×3, the legacy class name that must never be renamed**: instances already on users' home screens are found by component name) plus `Cell2x2WidgetReceiver` / `Cell2x3WidgetReceiver` / `Cell4x2WidgetReceiver` / `Cell6x3WidgetReceiver`, and the two maintained ones `Cell3x2WidgetReceiver` (3×2, default style 「接下来」) / `Cell1x2WidgetReceiver` (1×2, default style 「紧凑」). `WidgetProviderRegistry` marks the maintained tier: **only 3×2 and 1×2 are offered in the picker**; the other five keep their class, metadata, preview assets and manifest entry, but their receivers are **disabled at runtime** by `WidgetProviderScopeGate.apply(context)` (called from `MainActivity.onCreate`; idempotent — it writes only when the current state disagrees, with `DONT_KILL_APP`). Rationale: the picker's entry list is decided by component enabled-state, and the pin path cannot be trusted across OEM launchers. Accepted cost (product decision): home-screen instances of the five retired sizes freeze and may be dropped by the system on app update — no migration, no in-app warning. Rolling back means resetting those components to `COMPONENT_ENABLED_STATE_DEFAULT` in one pass, or the picker will never show them again. **Labels carry no style and no size**: both maintained entries are labelled 「课表」 and users tell them apart by the span label the launcher prints under the name (see the picker-label bullet below); the style words 「接下来 / 紧凑」 belong to the in-app panel, where the two cards must be distinguishable. Each has its own `res/xml/widget_info_<cells>.xml` (`targetCellWidth/Height`, `configure`, `updatePeriodMillis`, `previewLayout` + `previewImage`) and its own `android:label` (`@string/widget_label_<cells>`); all five share the **same** `ClassTrackWidget` composition, so nothing about rendering is duplicated. This exists because the pin size hint is ignored by launchers (previous bullet): registering the size in the provider metadata is the only way to let a user pick a size, and it makes the picker path independent of the pin callback (which OEM launchers drop). `WidgetProviderRegistry` (pure) is the single source of truth for 「which class ↔ which preset」; `WidgetProviders` (Android) adds the `ComponentName` plumbing and the cross-provider instance union used by the pin baseline/confirmation and the config page. Gates: `WidgetProviderRegistryTest`, the cross-layer assertions in `widgetPinPresets.test.ts`, and `scripts/check-android-assets.js#assertWidgetProviders` (five metadata files with matching `targetCell*`, five `APPWIDGET_UPDATE` receivers, legacy name still present). The picker previews are **generated**: `scripts/generate-widget-preview-layouts.py` emits the five `previewLayout` mocks and `scripts/generate-widget-preview-images.py` the five `previewImage` PNGs from the same metrics formulas — replacing the hand-written single mock, whose staleness comment had already drifted (it still claimed the 4×3 calibration after `W_REF/H_REF` moved to 2×2). Re-run both whenever `WidgetLayoutMetrics` constants, a provider's default style, or the calibrated sizes in `WidgetProviderRegistry` change.
- **`WidgetConfigActivity` is exported and therefore an attack surface**: it must treat `EXTRA_APPWIDGET_ID` as untrusted input — verify `AppWidgetManager.getAppWidgetInfo(id)` exists and `WidgetProviders.isOurs(info.provider)` (all registered providers — seven tiers since 2026-09-21, including the runtime-retired ones: an instance placed before the narrowing must still be configurable; hard-coding one of them silently rejects the rest with 「设置打不开」), otherwise `setResult(RESULT_CANCELED)` + `finish()` with no writes and no user payload. The rejection reason is a whitelisted enum (`invalid_widget_id` / `unknown_instance` / `foreign_provider`) so a real rejection can be told apart from a caller that simply forgot the extra (the extra is `appWidgetId`, not `appwidget_id` — a wrong key reads as `INVALID_APPWIDGET_ID` and looks exactly like a security rejection). It accepts no URL/file/payload extras, and its diagnostics log only a phase plus a whitelisted reason. The provider declares `android:configure="...WidgetConfigActivity"` and `android:widgetFeatures="reconfigurable"` for the placement-time and long-press paths.
- **The config page renders real course data, and that is an accepted residual risk** (changed 2026-09-19 after device review): the style thumbnails are real Glance compositions of the live schedule (see the preview bullet), so anyone who can start this exported Activity with a valid `appWidgetId` can see the user's timetable. The previous design avoided the entire class of problems by rendering no data; **the product owner replaced that boundary with WYSIWYG previews** after the static mocks were found to misrepresent the real widget. Keep the mitigations that remain (id-ownership check, no payload extras, payload-free logs) and do not add further data to this page without re-deciding the boundary. Do not "fix" this by whitelisting launcher package names — the configure Intent only carries an id, and launcher package names are not a verifiable trust anchor.
- **Three layout styles, chosen per instance** (R1/R8): `day_list` (summary row `今天 周六 · 共 N 节` + full-day list, in-progress row highlighted, finished per policy), `next_up` (hero card + the same list), `compact` (hero + `今天还有 N 节` + **the classes after the hero**; added 2026-09-21 — the tier is a tall narrow card, so only drawing the hero left a blank lower half). The follow-up rows are `rows[firstRowAfterHero ..]`, where `firstRowAfterHero` is the first not-finished row + 1 (all rows finished → none added), so finished classes can never appear in `compact`.
- **The widget is responsive by construction, not by size buckets** (changed 2026-09-19, **narrowed 2026-09-20**): `sizeMode` is `SizeMode.Exact`, so `LocalSize` is the host cell's real size and the layout adapts to any size the user drags the widget to. Do **not** reintroduce `SizeMode.Responsive(declaredSizes)` or any `if (height < N.dp)` threshold: declared size buckets make the composed layout depend on which bucket the host picked, which broke both the real widget and the config-page preview. The 2026-09-20 narrowing separates two things the old wording ran together — **still forbidden**: size *buckets*, and any size *threshold* that decides whether a block is shown or which day/rows the list reads. **Changed 2026-09-21 twice**: first the style was matched to the size (`AUTO` + `WidgetPreset.match(w, h)`), then — with the maintenance surface narrowed to two tiers — **that matching path was deleted** (`match` / `distanceTo` / `isPreferableTo` are gone). Now: `WidgetStyleConfig.DEFAULT_LAYOUT_STYLE = next_up`, `WidgetStyleResolver.effective(config, providerPreset)` returns the stored style when the user picked one, and otherwise the **provider preset's** style (`AUTO` — which historical instances may still store — resolves to the provider preset, i.e. 3×2 → 接下来, 1×2 → 紧凑). The enum value and its parsing stay so old rows never throw. The picker's size label is **not ours**: measured on Launcher3 (Android 16 image) the span it prints is `max(targetCell*, span derived from minWidth/minHeight)` — with `minWidth=90dp` the 1×2 entry was labelled 「2 × 2」, with `minWidth=60dp` it reads 「1 × 2」. So keep `minWidth` **below one column width** for a one-column tier (60dp) and never word copy as a promise about the size. The prohibition that remains is on `SizeMode.Responsive` / discrete buckets deciding the composed layout. **Now allowed**: deriving the metrics (font sizes, paddings, row gaps, column widths, corner radius) from `LocalSize` through one **continuous** function, `WidgetLayoutMetrics.resolve(w, h)` = `clamp(min(w / W_REF, h / H_REF), 1.0, 2.0)` with `padScale = sqrt(scale)`, pinned by `WidgetLayoutMetricsTest`. The lower bound is `1.0` on purpose: the pre-change literals are the values already validated on small cells, so `scale = 1` reproduces them exactly and every existing phone size stays pixel-identical. Also allowed: splitting the body into two columns **only** when the user picked 「双栏」 *and* the geometry permits it (`width >= 320dp && width >= height * 1.25`, both layout-feasibility floors, not content-visibility thresholds) — both arrangements render the **same line sequence**, so nothing can drift between the widget, the preview and the picker. The whole card shares **one** scroll axis — hero, summary row and course rows are items of the same `LazyColumn` (`ColumnScope.defaultWeight()`), so nothing stays pinned while the inside scrolls. Vertical breathing room is the list's first/last item, not the card's `padding`: padding on the card stays fixed during scrolling and reads as a permanent white strip at the top.
- **Clicks must be attached to the scroll container *and* to every list item** (device-reproduced regression, 2026-09-20): `LazyColumn` compiles down to a `ListView` inside the RemoteViews collection, and that `ListView` covers nearly the whole card. `AbsListView` consumes the touch stream for its own scrolling, so a `clickable` on the outer root column never fires — tapping the card silently did nothing and the app could not be opened. `WidgetBody` therefore puts the same `actionStartActivity(...)` on the `LazyColumn` modifier, on each item's `Box`, and on the two vertical spacing items (which cover the padding and any blank area below the content). Item-level clicks are the standard collection-widget pattern; keep them when touching this layout.
- **The collection `ListView`'s scrollbar is disabled by overriding Glance's *list style*, not its layout** (mechanism corrected 2026-09-20 after a device regression): the container hosting `LazyColumn` is a `ListView` whose default style draws a vertical scrollbar that fades in over the right edge of the course rows while dragging — no navigation value in a card with a handful of rows, and it covers the room column. The previous fix copied `res/layout/glance_list.xml` and added `android:scrollbars="none"`; that **silently stopped working on Android 13+**, because Glance 1.2.0 also ships 11 API-33+ variants (`res/layout-v33/glance_list_end_top.xml` etc.), each its own `ListView`, which the launcher inflates instead. The one place they all meet is `style="@style/Glance.AppWidget.List"` — an **empty style** in the library — so the app redefines it in `res/values/styles.xml` with `android:scrollbars=none`. **App-side resources override library resources of the same name**, which is what makes this work, and one style covers the base layout plus every v33 variant (and any future one). The style is version-coupled to the Glance artifact: on every Glance upgrade re-check that upstream's `Glance.AppWidget.List` is still empty (`unzip -p <aar> res/values/values.xml | grep 'Glance.AppWidget.List'`) and copy over any attributes it gained — attributes lost here are exactly how the widget would lose upstream behaviour.
- **The two-column body keeps one line sequence, and its left card is the only "sub-card"** (added 2026-09-20): `DualColumnBody` renders the *same* `WidgetBodyPlan` lines the single-column path renders — the hero line moves into a left card, the remaining lines go into the right column's `LazyColumn`; nothing is added or dropped (design D11). The left card is the **only** place that draws an inner surface with a fixed row structure, and it fills its column (`fillMaxHeight`) with the top block (status label + course name) pinned to the top and the bottom block (time · room + 「今天还有 N 节」) pinned to the bottom, the slack absorbed by `Spacer(GlanceModifier.defaultWeight())` — Glance's `Column` has **no** `verticalArrangement`, so `Arrangement.SpaceBetween` is not an option. **Do not** wrap the single-column hero in such a card: it was implemented, reviewed on a real tablet, and rejected by the product owner — on a single-column card it replaces blank space with card padding and adds a frame that carries no meaning. Corollary, learned the hard way: **never give a text container a height estimated from its content** (font size × line height). Glance cannot measure text, the estimate was smaller than the real line box, and the hero's first line was clipped on the phone. Let content size itself; only a container that genuinely spans a whole column may distribute slack with a weighted `Spacer`.
- **Course rows have a form, decided by the judgment layer** (added 2026-09-21): `WidgetBodyPlan.RowForm` = `STANDARD` (time column + name + right-aligned classroom) / `TWO_LINE` (time column + name, classroom below — used by the two-column right pane, specified explicitly by the renderer) / `COMPACT` (name on one line, 「time · classroom」 below, no time column — the 1×2 tier). Reason: in 82~105dp of width a fixed time column (plus the in-progress marker column) leaves ~35dp for the name, so 「线性代数」 was clipped to 「线性代…」, and pushing the classroom to the right edge made it collide with the name. The height estimate must follow (`RowForm != STANDARD` → 2 lines), otherwise the fill plan over-estimates the free space and inflates the fonts. The compact hero detail is likewise **two lines** (time / classroom) via `WidgetBodyLine.hero(titleMaxLines, stackedDetail)` + `HeroDetail(stacked = …)`: on one line the narrow tier clipped 「14:00 - 15:35 · C305」 down to 「14:00 - …」, which lost exactly the classroom — and a classroom must never be dropped (product requirement).
- **Body content is a pure line sequence** (`bodyLines(state, style, plan)` → `List<BodyLine>` rendered by one `BodyLineView`): the real widget puts it in a `LazyColumn`, the config-page preview puts the same sequence in a plain `Column` because `LazyColumn` needs the launcher's `RemoteViewsService` and renders empty outside a host. Adding or reordering a line therefore cannot make the preview drift from the widget. The hero course name is **one line** (`maxLines = 1`): two wrapped lines eat the space that belongs to the remaining courses, which is exactly the trade-off users complained about.
- **`LazyColumn` is the only experimental opt-in besides the preview renderer**: one `@OptIn(ExperimentalGlanceApi::class)` for the scrolling list and one `@OptIn(ExperimentalGlanceRemoteViewsApi::class)` in `WidgetPreviewRenderer`. Both are official opt-in mechanisms, not suppressions; keep the count at two (see design D15). Rare launchers that cannot host collection widgets should fall back to height-truncated rows with a `+N` trailer.
- **Rendering must always read the latest resolved state (`WidgetRenderCache`)**: Glance invokes `provideGlance` only once per session; `update`/`updateAll` re-compose `provideContent` with the captured closure. If the composition reads the captured `state`, a time change or new snapshot pushes a refresh yet the pixels stay on the previous frame (device-reproduced defect, fixed 2026-09-19). Every refresh path converges on `WidgetRefreshController.resolveCurrentState`, which publishes the result into `WidgetRenderCache` (a process-local Compose `mutableStateOf`, written under `Snapshot.withMutableSnapshot`); `provideContent` reads `WidgetRenderCache.latest()` with the `provideGlance` result as fallback for the very first render.
- **The day-list phase model (R9)**: the resolver marks every today entry `FINISHED` / `IN_PROGRESS` / `UPCOMING` and exposes counts (`todayRemainingCount`, `todayFinishedCount`). The three finished policies (`show_dim` / `hide` / `collapse`) are a pure Java function (`WidgetDayListPolicy`) so they are JUnit-tested; the renderer only draws what the policy returns. The `compact` style only ever lists classes **after** the hero (finished rows sit before it), so the finished-policy has no visible effect on it; the config UI disables it with a note that states **that** reason, not the (now false) 「compact shows no list」.
- **The day-selection rule (R11) is one pure function** (`WidgetDayPlan.resolve(todayItems, nextDayItems, finishedPolicy)` in Java, JUnit-tested): today has visible rows → list today; today has rows but the policy hides them all → show "今天已无课" and do **not** fall back to tomorrow (the user just asked for those rows to be hidden); today has no classes and tomorrow does → list tomorrow with the summary saying 「明天 周三 · 共 N 节」; neither day → no course rows at all, only the summary line plus the 「下一节 · 10月8日 周四 08:00 …」 hint. Long holidays therefore never turn into a fake class list. `WidgetDisplayState.nextDayItems` exists solely to feed this rule and is produced by `WidgetStateResolver` from `dayOffset + 1`.
- **Preview (R10, changed 2026-09-19 to WYSIWYG)**: the config-page thumbnails are **real Glance compositions** — `WidgetPreviewRenderer` composes the same `WidgetContent` through `GlanceRemoteViews.compose(context, size, null, Bundle.EMPTY)` and the Activity mounts the resulting `RemoteViews` in a `FrameLayout` (scaled down to the slot). The composition size is the instance's real cell size read from `OPTION_APPWIDGET_MIN_WIDTH/HEIGHT` (this is only truthful because `sizeMode` is `Exact`; with `Responsive` the widget composed at a different, smaller bucket size and the preview lied about the content). Two device-reproduced pitfalls are load-bearing: (a) inflate the `RemoteViews` with `applicationContext`, never the Activity — an `AppCompatActivity`'s inflater rewrites framework views into `AppCompat*` classes and `RemoteViews.apply()` then throws `ActionException: view: androidx.appcompat.widget.AppCompatImageView can't use method with RemoteViews`, killing the process; (b) the static mocks `widget_preview_next_up/compact` were deleted because keeping two renderers in sync is what let them drift. `WidgetPreviewRenderer.render` catches `RuntimeException` and the Activity wraps `showPreview` too, so a preview failure never blocks saving a style. Only the picker's per-provider `android:previewLayout` (`widget_preview_<cells>.xml`) plus `android:previewImage="@drawable/widget_preview_<cells>"` remain static — and both are now **generated** from the metrics formulas (see the five-providers bullet), so they cannot drift from each other. Each file's header states its calibration (scale / padScale for that cell size) and that it must be regenerated when the metrics or the default style change; the layouts use RemoteViews-whitelisted classes only, and XML comments must not contain `--` (aapt rejects it — the generator asserts against it after a `--check` mention slipped through). **Mock honesty rules** (2026-09-21): every `TextView` in a generated mock carries `maxLines="1"` + `ellipsize="end"` (the generator only adds what is missing — inserting blindly produced duplicate attributes and aapt rejected the build with `AttributeNSNotUnique`), because the runtime renders each line with `maxLines = 1`; a mock without them folded 「接下来 · 第 3-4 节」 into five lines in a 82dp column, i.e. it looked worse than the real widget. And the sample copy must be copy the runtime can actually produce: `widget_preview_hero_label` is 「正在进行」 (the in-progress hero label), not 「正在进行 · 第 3-4 节」, which never existed at runtime. The 1×2 mock mirrors the real compact composition (two-line hero detail: time / classroom, counter, then the follow-up classes in the narrow row form). `python3 scripts/generate-widget-preview-layouts.py --check` verifies the layouts on disk match the generator.
- **Browser/PWA isolation is load-bearing**: `Capacitor.isPluginAvailable('WidgetSnapshot')` returns **true on the web** because our own `WebPlugin` fallback registers it. Therefore the guard must be `Capacitor.getPlatform() === 'android' && isPluginAvailable(...)`. Dropping the platform check sends browsers down the real sync path.

### 4. Validation & Error Matrix

| Condition | Required behavior |
|---|---|
| Browser / PWA / iOS, or plugin missing | Whole feature is a no-op. Sync hook returns early, settings card renders nothing, no bridge call, no console error. |
| `snapshotJson` missing/empty | Reject `INVALID_PAYLOAD`; do not write. |
| Payload > 256 KiB | Reject `PAYLOAD_TOO_LARGE` without writing; Web side should have self-checked first. |
| Not valid JSON / `schemaVersion !== 1` / unknown `status` / `entries` or `dayEndEpochMs` not arrays / > 800 entries | Reject `INVALID_PAYLOAD`; do not write. |
| One entry has a missing or mistyped field | Skip that entry only; the rest of the snapshot stays usable. Native never fails a whole snapshot because of one bad row. |
| `commit()` returns false | Reject `STORAGE_ERROR`; never `resolve()` a write that did not land. |
| Stored snapshot absent | `MISSING` → widget prompts the user to open the app once. |
| `now > validUntilEpochMs`, or no day in `dayEndEpochMs` contains `now`, or `now < generatedAtEpochMs - 6h` (clock rollback) | `STALE` → prompt to re-sync. Never guess a course. |
| Snapshot valid but no `endEpochMs > now` | `NO_UPCOMING` → "semester finished", not "no data". |
| Exact-alarm permission missing or revoked | Skip L3 silently, keep L4/L5 working. `SecurityException` from `setExactAndAllowWhileIdle` must be caught. |
| Render throws inside a broadcast receiver path | Catch it, log a phase, keep the process alive; the next scheduled boundary retries. |

### 5. Good / Base / Bad Cases

- **Good**: the user imports a timetable, the Web layer builds a snapshot covering the rest of the semester and pushes it once; the widget immediately shows the next class, then switches at each class boundary for the following weeks even if the app is never opened again.
- **Base**: the app was never opened → the widget shows "open ClassTrack to sync", which is honest rather than an empty card. A browser user sees no widget UI at all.
- **Bad**: native re-derives "which week is it" from `currentWeek` and the device clock (two sources of truth that drift); the widget shows "no class today" for a day whose courses were dropped by truncation; or the exact-alarm path throws `SecurityException` on a device where the permission was revoked mid-flight.

**用 adb 驱动 launcher 的两个可复用手法**（合成手势与真实手势差异会导致误判，这里是实测可行的写法）：

```bash

#    手柄坐标从截图换算（1080x2400 截图 displayed 900x2000 → ×1.2 得设备像素）。
adb shell input swipe 300 800 300 800 1200          # 长按实例空白处（别按到卡片上的按钮）

adb shell input motionevent UP 540 1400              # 落在桌面空白格 → 放置完成并弹出 WidgetConfigActivity

# 3) 判定"有没有留下实例"别靠截图：数 dumpsys 里的条目数

```

**尺寸下限由 provider 自己声明决定，且每档一份**：`res/xml/widget_info_<cells>.xml` 的 `minWidth/minHeight`（3×2 是 110dp/110dp；**1×2 特意是 60dp/110dp**，低于一列宽，否则 launcher 会把它标成/放成两列）。一列宽 = 屏宽px ÷ (density ÷ 160) ÷ 列数：AOSP 模拟器 1080px/420dpi/5 列 = 82dp，一加 Ace 5 Pro（ColorOS 15，默认 4×6 布局）≈ 105~112dp；改分辨率（1080×2400 → 1080×2376）不影响列宽。文案里的「2x1 / Compact」指的是**紧凑样式**，不是格子尺寸，讨论尺寸问题时不要把两者混在一起。

**日志读法**：每次 `phase=widget_sized` 之后常紧跟另一条 `widget_sized`（高度 = 配置页预览画布高度、宽度不受约束，如 `w=850 h=169`），那是宿主侧预览/缩放代理的渲染，**不是**桌面实例尺寸；桌面实例尺寸要与截图量测互相印证（`w=179 h=210` ↔ 2×2 格）。
