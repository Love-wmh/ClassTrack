# 小工具：失败即弹醒目标态框 + 按尺寸注册五个 provider + 尺寸变化自动匹配

## Goal

真机（PKR110 / ColorOS）实测确认：**系统会静默丢掉 `requestPinAppWidget` 请求**（launcher 起了
`AddItemActivity` 却从不置前，也没有确认回调）。上一轮已经做到「不撒谎」（超时后如实告知），
但失败反馈仍然只是面板底部一行灰字，用户很容易滑过去。同时，应用内入口这条路径在这类桌面上
**注定不可靠**。

本任务做两件事：

1. **失败即弹醒目标态框**：点击「添加到桌面」立刻弹模态（先「正在尝试添加」），一旦判定失败
   （被取消 / 系统不支持 / 系统没弹确认界面 / 10 秒无回调）**立刻**切成失败态，给出手动步骤。
2. **按尺寸注册五个小工具 provider（2×2 / 2×3 / 4×2 / 4×3 / 6×3）**：让用户能在**系统拾取器**里按尺寸选，
   放下即带对应样式 —— 这条路不依赖 pin 回调，因此在 ColorOS 上也能真的放下。
3. **尺寸变化后自动匹配预设**（产品 2026-09-21 要求「改尺寸后要匹配上」）：实例默认按当前尺寸匹配样式与行项形态；
   用户在配置页显式选过样式后不再自动变（**手动优先**）。此条推翻了早先「不按尺寸决定内容」的口径，见 R4。

## 背景与现场约束（沿用上一轮结论）

| 事实 | 后果 |
|---|---|
| `requestPinAppWidget` 返回值 ≠ 放下；失败无回调 | 只能靠「确认回调」判定成功，靠超时/探针判定失败 |
| ColorOS 起 `CONFIRM_PIN_APPWIDGET` 的 `AddItemActivity` 却**从不置前** | 应用内入口在这台机器上必然失败 → 必须给一条可靠的替代路径 |
| 拾取器里的尺寸标签来自 provider 自己声明的 `targetCellWidth/Height`（实测显示「4 × 3」） | **多 provider 才能真正控制尺寸**：pin 的 extras 会被 launcher 忽略 |
| 一个 `GlanceAppWidget` 可以被多个 receiver 共享 | 多个 provider 不必复制渲染逻辑，样式状态仍按 `appWidgetId` 隔离 |

## Requirements

### R1 模态框：点击即弹，失败立刻切态

- 点「添加到桌面」→ 立即弹**模态**，状态 `requesting`：标题「正在尝试添加…」+ 明确指引
  （「如果系统弹出确认窗口，请点『添加』」）。
- **不等待满 10 秒才给失败反馈**：失败一旦**判定出来**就立刻切态（见 R2 的探针）。
- 失败态必须**醒目**（模态标题 + 图标 + 一句话原因），并包含：
  - **按尺寸指明该选哪个**（五个 provider 标签逐字：`课表 · 极简 2×2` / `课表 · 手机 2×3` / `课表 · 宽横 4×2` / `课表 · 标准 4×3` / `课表 · 宽屏 6×3`）；
  - 手动步骤全文（长按桌面空白处 → 小工具 → 找到课表 → 拖到桌面上，再按卡片上的格子数调整大小）；
  - 「再试一次」与「知道了」两个操作。
- **成功之前绝不出现任何成功措辞**（沿用上一轮的核心约束）：只有确认回调到达才显示成功，并自动关闭模态。
- 模态可关闭；关闭后不重复打扰同一次失败（除非用户再点一次）。

### R2 失败判定要快（探针）

- 已确定的失败：`supported=false`（系统不支持）、`requested=false`（被取消）→ **立即**失败态。
- 新增**快探针**：请求发出后约 2 秒内，若我们的 Activity **从未退到后台**
  （即 launcher 的确认界面压根没出现）→ 判定为「系统没有弹出确认界面」→ 立刻切失败态。
  - 判定口径必须写成**纯逻辑**（`PinAttempt.shouldFailFast(requestedAtMs, nowMs, backgroundedAtMs)`）并由 JUnit 钉住。
  - 文案必须诚实：这是**推断**，所以要写「系统没有弹出确认界面」并附「如果你在桌面上看到了确认界面，请先把它点完」，
    而不是断言失败。
  - **失败态之后仍继续监听回调**：若回调稍后到达 → 切成成功并关闭模态（不能因为已经"宣布失败"就忽略真成功）。
- 兜底：10 秒仍无回调 → 沿用上一轮的如实文案（「系统没有完成添加（部分厂商桌面会忽略这个请求）」）。

### R3 五个 provider：2×2 / 2×3 / 4×2 / 4×3（宽度够就双栏）/ 6×3

- 五档尺寸各注册一个 provider（各自独立的 receiver 类 + `*_widget_info.xml` + 拾取器预览 + 标签）：

  | provider | 标签 | targetCell | 默认样式（= 同尺寸的预设） |
  |---|---|---|---|
  | 2×2 | `课表 · 极简 2×2` | 2 × 2 | 极简单栏 + 「下一节」一行 |
  | 2×3 | `课表 · 手机 2×3` | 2 × 3 | 手机主力位：单栏、行项两行 |
  | 4×2 | `课表 · 宽横 4×2` | 4 × 2 | 单栏、横铺、行项两行 |
  | 4×3 | `课表 · 标准 4×3` | 4 × 3 | **双栏能力**：宽度 ≥ 320dp 且 宽 ≥ 高×1.25 时双栏，否则单栏 |
  | 6×3 | `课表 · 宽屏 6×3` | 6 × 3 | 双栏 + 更宽右栏（教室跟在课名下） |

- **两个旧预设里的 4×3 合成一个**（产品决定）：手机 4×3（373×321，比例 1.16）自然退化成单栏，
  平板 4×3 自然分两栏，因此一个条目覆盖两种情形，拾取器里不会出现两个都标 `4 × 3` 的条目。
- 五个 receiver 共用同一个 `ClassTrackWidget`（渲染逻辑不复制），样式状态仍按 `appWidgetId` 隔离。
- **放置即带样式**：某个 `appWidgetId` 从未配置过时，用**它的 provider** 决定默认样式
  （`AppWidgetManager.getAppWidgetInfo(id).provider` → 预设）——这比「猜新实例」确定，也不需要 pin 回调。
- 应用内 pin 面板同步为这**五张卡**（`2×2 / 2×3 / 4×2 / 4×3 / 6×3`）：档位不删，只是把两个 4×3 合成一个。
- 尺寸与字号的连续性不变（`WidgetLayoutMetrics.resolve` 仍按 2×2 参考格、上下界不变）。

### R4 尺寸变化后自动匹配预设（**口径变更，显式记录**）

> **这条推翻 2026-09-20 的「禁止任何按尺寸阈值决定显示哪一块/读几行」口径**（产品 2026-09-21 明确要求：
> 「当用户更改尺寸后要匹配上」）。变更范围**仅限「选择样式预设」**：仍然禁止 `SizeMode.Responsive`，
> 与任何「用离散档位决定合成布局」的做法。

- 实例默认处于**自动**状态：按**当前尺寸**匹配最合适的预设（含单/双栏与行项形态），尺寸一变就重匹配。
- **手动优先**：一旦用户在配置页显式选了样式，该实例不再自动匹配（用户的选择永远赢）。
- 匹配必须是**连续最近邻**（对每档预设的标定尺寸算距离取最近），不引入 `if (height < N.dp)` 这类阈值分支；
  规则写成纯函数（`WidgetPreset.match(widthDp, heightDp)`）并由 JUnit 钉住（含边界与并列取小档）。
- 实现口径：`layout_style` 缺省或为 `auto` ⇒ 样式、宽格表现、行项形态都随尺寸；显式值 ⇒ 该样式赢，
  `wide_layout` 仍按其自身设置生效（既有语义不变）。
### R5 安全与既有约束不回退

- `WidgetConfigActivity` 的 id 归属校验必须接受**我们所有** provider（现在是单 provider 硬编码 —— 多 provider 后
  若不改，第二个 provider 的实例会被判为"不属于我们"而拒绝配置）。
- pin 基线与「回调后实例集合」必须**跨所有 provider** 取并集。
- 冻结快照契约（`schemaVersion = 1`）不动；日志只含阶段名/数值/白名单枚举。
- 拾取器预览：每个 provider 一份，内容必须与该 provider 的默认样式一致，且随 `W_REF/H_REF` 标定同步
  （沿用「静态预览要手写同步」的既有约定，并在文件头注明同步条件）。

### 非目标

- 让 ColorOS 弹确认界面（launcher 行为，做不到）。
- **`SizeMode.Responsive` 与任何「用离散尺寸档位决定合成布局」的做法**（R4 允许的只是用连续最近邻挑选预设；间距/字号仍走连续度量）。
  注意 R4 已按产品要求放开「尺寸变化 → 自动匹配预设」，这一条非目标只保留「档位化」的禁令。
- 自动打开配置页（有些 launcher 会自己拉，我们主动拉会与它竞争）。

## Acceptance Criteria

- [ ] **A1 模态状态机有测试**：`useWidgetPin` 的状态（`requesting` / `added` / `cancelled` / `unsupported` / `no_confirmation` / `unconfirmed`）
  与文案由 vitest 的纯函数测试钉住，含「requesting 文案绝不含『已添加』」「失败态文案含按尺寸的手动步骤」。
- [ ] **A2 快探针有 JUnit 覆盖**：`PinAttempt.shouldFailFast` 覆盖（未退后台且已过 2s → 失败；退过后台 → 不判失败；未到 2s → 不判失败；时钟回拨/负数 → 不判失败）。
- [ ] **A3 五个 provider 注册正确**：`WidgetProvidersTest` 钉住「恰好五个 provider」「组件 ↔ 预设一一对应（含 4×3 那个 provider 的双栏能力）」；
  `scripts/check-android-assets.js` 增加对 APK 内五份 info XML 的断言（存在 + `targetCell` 分别为 2×2 / 2×3 / 4×2 / 4×3 / 6×3），
  并由 vitest 读真实资源文件断言「provider 标签 / targetCell ↔ TS 预设」逐字一致。
- [ ] **A4 放置即带样式**：新实例未配置时按 provider 取默认样式（JUnit 覆盖映射；真机/模拟器五个 provider 各放一个，样式与各自预览一致）。
- [ ] **A5 配置页与 pin 链路对多 provider 正确**：`WidgetConfigActivity` 接受**五个** provider 的实例；
  pin 基线与目标集合跨 provider 取并集（JUnit 或既有测试覆盖 + 真机验证）。
- [ ] **A6 尺寸变化自动匹配（R4）有测试**：`WidgetPreset.match(w, h)` 的最近邻规则 JUnit 覆盖（各档中心、档间边界、并列取小档、极端尺寸）；
  「显式样式优先于自动」的不变式有测试。
- [ ] **A7 真机复验**：PKR110 上（a）点击后**立即**出现「正在尝试添加」模态；（b）失败态在探针命中后**立即**出现（不再等满 10 秒）；
  （c）拾取器里能看到**五个** ClassTrack 条目且尺寸标签分别为 2×2 / 2×3 / 4×2 / 4×3 / 6×3；（d）从拾取器放下的实例带对应样式；
  （e）**拖动改变尺寸后样式自动匹配**（例如 4×3 ↔ 6×3 之间拖动，单/双栏与行项形态随之变化），且在配置页手动选过样式后不再自动变。
- [ ] **A8 门禁**：`testDebugUnitTest` / `pnpm test` / `pnpm lint` / `cap:build:android` 全绿；既有 157 例不回归。

## Notes

- provider 是**五档尺寸**（2×2 / 2×3 / 4×2 / 4×3 / 6×3）各一个；旧预设里的两个 4×3 合成为一个（产品决定），
  2×3 是产品指定的手机主力位；因此面板是五张卡。
- 手机那个 provider **沿用旧类名** `ClassTrackWidgetReceiver`（映射到 4×3）：改名会让桌面上已有实例全部失效。
- R4 是由产品明确要求引入的**口径变更**（「改尺寸后要匹配上」），范围仅限挑选预设：仍然禁止 `SizeMode.Responsive`
  与离散档位决定布局；匹配规则必须是连续最近邻且可测。
- 探针是**推断**而非事实：宁可说「系统没有弹出确认界面」并保留「请先把它点完」的提示，也不要断言失败。
