## 3. 文字块宽度可以超过卡片内边距盒（只校验高度）

`ScheduleCourseCell.apply()` 收窄内层块时用 `Range.getClientRects()` 实测「最长行 ink 宽度」并写 `block.style.width`，**收窄后的校验只判高度**（`if (!fits()) block.style.width = ''`），不判宽度。

实测「概率与统计 (Python)」卡（列 x 608..764）：

| 项 | 实测 |
| --- | --- |
| 卡片外框 | x 613..759（144 设备px = **41.1 CSS px**） |
| `ring-2` 描边带 | x 613..623（≈ 10 设备px ≈ **2.9 CSS px**） |
| `px-1.5` 后的内边距盒 | x ≈ 634..738（**29.1 CSS px**） |
| 文字 ink 范围 | x **624..749**（**36 CSS px**） |
| 溢出量 | 左 10 设备px / 右 11 设备px ≈ **左右各 3 CSS px** |

→ 文字块宽度超出内边距盒约 3 CSS px/侧。**成因（代码级，已确认）**：内层块宽度由 `block.style.width = Math.ceil(used)px` 实测写入，而 `overflow-wrap: break-word` **不降低 min-content**；`(Python)` 这种不可断 token 的 min-content ≈ 37 CSS px > 内边距盒 29.1，块被撑宽后只做了高度校验（`if (!fits()) block.style.width = ''`），没有宽度上限。

> ⚠️ **`overflow-hidden` 的实际裁剪边界待实现阶段用浏览器实测确认**：按 CSS 规范 `overflow: hidden` 应在 padding box 处裁剪，那样这 3px 只会表现为「字形贴边」；像素分析在描边带与字形 AA 之间无法完全区分（描边半透明白压在同色底上，与字形灰阶重叠）。此项不影响结论——真正的缺陷是「只校验高度、不校验宽度」，无上限的实测宽度本身就是不稳定来源。

## 4. 纵向零余量

```
可用高度 = 794（视口） − 24（px-2/py-3 上下） − 48（顶栏 h-9 + mb-3） ≈ 722 CSS px
网格需求 = 36（表头） + 12 × 62 = 780 CSS px
```

→ 780 > 722，**每节行高卡在 `3.875rem` 下界、`1fr` 分不到任何余量**。截图底部能看到第 9 节行只露出一部分（连通域最后一块 y 2376..2454、高仅 78 设备px）——**这是可纵向滚动的预期行为，不是缺陷**（滚动容器是 `overflow-x-auto overflow-y-auto`）。

但它带来两个真实影响：① 纵向**没有任何弹性**，任何系统级尺寸扰动（系统栏高度、显示大小、字体缩放）都会立刻改变可见节数；② 逐格测量的「放得下吗」判断只剩 ~3 CSS px 余量（见 §2 的隐式推论），测量时机的抖动足以让同尺寸格子得到相反结论。

## 6. 顺带实测到的结构浪费

- **周六 / 周日两列全空但等宽占用**：该用户课表只在周一–周五有课，7 列等宽 → **28% 的横向空间被永久浪费**，直接加剧了 29.6px 可用文字宽的紧张。
- 卡片描边 `ring-2` = 2 CSS px，占卡片外框 41.1px 的 **4.9%**；出勤角标 `size-3` = 12 CSS px，占列宽 44.6px 的 **27%**。
