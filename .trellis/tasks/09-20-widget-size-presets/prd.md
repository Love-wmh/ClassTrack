# 小工具预设尺寸与 App 内「添加到桌面」入口

## Goal

上一轮把「度量随格子尺寸连续自适应」做完了，但真机上依旧是「大格子里一半是空白」：平板 4×3 的左卡中缝约
195dp、右栏底部约 210dp（合计占卡片一半）。根因不是度量没跟上，而是**内容量固定、格子变大**，而
「任意尺寸都显示完美」既做不到（Glance 拿不到文本测量）也不值得做。

本任务换一条路：**只承诺少数几个预设尺寸显示完美，其余尺寸按现有连续度量尽力渲染（不做承诺）**；
同时把「添加小工具」从桌面长按搬到**应用内**，让用户一键按预设添加，从源头避免「自己拖出一个没人验证过
的尺寸」。

## Requirements

### R1 预设定义（产品承诺面）

一个**预设** = 目标格子尺寸 × 布局样式 × 大格子表现 × 填充策略。首批四个：

| 预设 | 目标格子 | 布局样式 | 大格子表现 | 填充策略 |
|---|---|---|---|---|
| 手机 · 极简 | 2×2（179×210dp） | 紧凑 | 跟随尺寸 | 不动度量（现状 46%），只保证不溢出 |
| 手机 · 标准 | 4×3（373×321dp） | 接下来 | 跟随尺寸 | 余量摊到行距与首尾留白（不动字号）→ 75% |
| 手机 · 宽横 | 4×2（373×210dp） | 接下来 | 跟随尺寸 | 天然就满（内容 97% 已有），不做额外填充 |
| 平板 · 双栏 | 4×3（733×419dp） | 接下来 | 双栏 | **静态富内容**（见 R2.1）+ 余量均摊 → 98% |
| 平板 · 宽屏 | 6×3（1142×419dp） | 接下来 | 双栏 | 同「平板 · 双栏」，只是右栏更宽 → 98% |

**全部预设都只渲染「今天」**：不接明天、不做两天视图（原方案已否）。

- **预设内完美**：在预设目标尺寸上，内容纵向占比达到设计目标（各预设的目标值写在 design D2，验收时用截图量测）。
- **预设之外不承诺**：用户把实例拖到别的尺寸后，按现有连续缩放尽力渲染即可，不做「必须铺满」的承诺。
  这条是范围收缩，必须写进配置页/文档的诚实说明里，不能让用户以为拖到任意尺寸都完美。
- 预设**不改变内容语义之外的东西**：用户仍可在配置页自由改用其它样式/表现（预设只是一次性的推荐组合）。

### R2.1 静态富内容（取代「接明天」与「倒计时」，是本次的主要填充手段）

四项内容全部由**渲染时刻已有的数据**算出，不需要新增任何闹钟/刷新（这是它被选中的原因）：

| 项 | 内容 | 数据来源 |
|---|---|---|
| 课程行改双行 | 第一行课名、第二行「第 3-4 节 · 教室」 | 快照 `sections` / `classroom` |
| 行状态标记 | 正在进行高亮 + 该行加高；已上完变暗 | 既有 `WidgetDayItem.phase` |
| 汇总行两行 | 「今天 周日 · 共 4 节」+「已上完 1 节 · 还有 2 节」 | 既有 `todayFinishedCount` / `todayRemainingCount` |
| 列表底部一行 | 「今天最后一节 19:00 数据结构 A101」 | 当天最后一项 |
| 双栏左卡中缝 | 「下一节 16:00 线性代数 D402」+「第 1 周 / 共 20 周」 | 当天下一个 `UPCOMING`；周次来自既有 `currentWeek`/`maxWeek` |

- **被否方案**：接明天（产品否）、「还有多久下课」倒计时与进度条（用户否：「不能实时就算了」——Glance 没有
  Chronometer 这类自走控件，倒计时准确性=刷新频率，会与省电的刷新梯冲突）。
- 双行行项与加高行是**预设属性**，不是按尺寸动态决定：手机两个预设仍是单行行项（保证手机不回归）。

### R2.0 字号是自变量，尺寸越大越大（2026-09-20 产品负责人追加）

- 参考格子从「手机 4×3」改为「**2×2 最小格（179×210dp）**」：`sizeScale = clamp(min(w/179, h/210), 1, 2)`。
  于是手机 4×3 的字号从 16sp 变成 ≈24.5sp、平板 4×3 到 ≈26sp —— **这是产品明确要求的效果**，不是回归。
- 课名**按宽度自动换行**（手机 2 行、双栏左卡 2 行），不再截断成「毛泽东思想和中国特色社会主…」。
- 字号停在「刚好放下」处（`fitScale`），所以不会为了字号大而裁字。
- 不回归口径随之收窄：**2×2 逐像素不变**（`sizeScale` 恒为 1.0、且不启用任何富内容），手机 4×3 允许变化。

### R2 填充模型：内容固定，度量与留白随格子连续变化

- 允许：度量（字号/行高/行距/内边距）随真实格子尺寸**连续**变化；余量按**解析式**计算并分配。
- 仍然禁止（继承上一轮 D16 收窄修订）：`SizeMode.Responsive`、任何「按尺寸档位决定显示什么内容/读几行/
  读哪一天」的分支。**「预设」不是尺寸档位**：预设决定的是「内容组合 + 目标填充率」，同一预设下无论格子多大，
  渲染的都是同一份行序列（装不下就滚动），不随尺寸增删信息。
- 硬约束：Glance 拿不到文本测量，**任何高度估算都必须保守**；上一轮用「字号 × 1.45」估算主卡高度导致真机上
  hero 首行被裁，这类做法不得重演（只允许放大**不承载文本**的间距，或对字号施加带余量的上限）。

### R3 应用内「添加到桌面」入口

- 入口放在**课表首页顶栏**（用户选定），并**顺带把顶栏按钮紧凑化**（现状 `h-10 w-10` 偏大）。
- 点击后给出四个预设卡片：名称、目标格子、一句话说明、示意；每张卡片一个「添加到桌面」按钮。
- 技术上走 `AppWidgetManager.requestPinAppWidget`（Android 8.0+，`isRequestPinAppWidgetSupported()` 为真时）。
  **尺寸提示（`OPTION_APPWIDGET_MIN_WIDTH/HEIGHT`）是否被 launcher 采纳必须先实测**；不采纳时降级为
  「预设 = 样式组合 + 推荐尺寸」并在卡片上写明目标格子（用户自己拖到该尺寸）。
- 不支持 pin 的环境（浏览器 / PWA / iOS / 老 launcher）：入口整体隐藏或降级为「手动添加」图文说明，
  与既有「小工具能力卡片仅在 Android 原生渲染」的口径一致。

### R4 预设应用到新实例

- pin 之前把选中的预设写入一个**待消费槽位**（沿用 `WidgetPendingRoute` 的既有范式），新实例的配置页
  打开时用它预填选项（用户仍可改），保存后写入该实例自己的状态。
- 若 launcher 直接以默认尺寸绑定且不弹配置页（`android:configure` 存在时通常仍会弹），待消费槽位
  必须有超时/一次性语义，不能影响后续新增的实例。

### R5 不回归（边界已变更，必须写清）

- **手机 2×2**：仍是「逐像素不变」的硬要求（预设策略就是不动度量）。
- **手机 4×3**：属于预设之一，允许因「余量均摊」产生变化；需要前后对比截图 + spec 更新，不再要求逐像素一致。
- 三种布局样式 × 三种「已上完」策略在**同一尺寸同一预设**下的行序列不变（JUnit 钉住）。
- 未使用新入口、未改任何配置的存量实例：行为与上一轮一致（除手机 4×3 的余量均摊）。

### R6 不改数据契约

不修改 Web → 原生冻结快照契约（`schemaVersion = 1`），不新增跨层字段。预设、待消费槽位都是原生侧状态；
静态富内容全部用快照里已有的字段（`sections` / `classroom` / `phase` / 当天计数 / `currentWeek`）。

### 约束

- C1 日志只含阶段名/数值/白名单枚举，**不含课程名、教室、时间**。
- C2 不新增实验性 API 的 `@OptIn` 数量（全模块 `ExperimentalGlanceApi` 与
  `ExperimentalGlanceRemoteViewsApi` 各一处）。
- C3「紧凑」样式仍然不显示列表；新预设不得让它长出列表。
- C4 首页顶栏紧凑化必须保持触控目标可用（不小于既有移动端规范的 40px 高度）与现有可访问性标签。

### 非目标

- 不为**任意**尺寸做到完美（只在四个预设尺寸上验收）。
- **不做任何需要新刷新的内容**：倒计时、进度条都否掉（Glance 无自走控件；用户明确「不能实时就算了」）。本次填充只用渲染时刻已有的数据。
- 不在小工具里显示教师/周次：快照没有这两个字段，属跨层契约升级。
- 不做 iOS / PWA 侧入口。

## Acceptance Criteria

- [ ] **A1 预设模型有 JUnit 覆盖**：预设表解析、目标尺寸上的度量取值、预设之间按尺寸插值连续、非法/缺失预设回退默认。
- [ ] **A2 填充算法的安全性有断言**：解析式计算出的内容高度在预设尺寸上不超过可用高度（不裁切）；余量分配有上限；字号放大有上限且留保守余量。
- [ ] **A3 内容语义不变**：同一预设同一尺寸下，三种样式 × 三种策略的行序列与上一轮逐一一致（「宽屏」预设的「今天+明天」作为该预设的固定行序列单独断言）。
- [ ] **A4 门禁全绿**：`testDebugUnitTest`、`pnpm cap:build:android`、`pnpm android:check-assets` 通过；Web 侧改动限于首页顶栏与入口（有对应测试）。
- [ ] **A5 五个预设尺寸的设备证据**：手机 2×2 / 手机 4×2 / 手机 4×3 / 平板 4×3 / 平板 6×3 各一张截图 + `phase=layout_fill`（含预设名、余量、行距、字号放大与填充率），并量测内容纵向占比达标（平板两档 ≥90%）。
- [ ] **A6 手机 2×2 逐像素不变**：与上一轮基线逐像素比对，差异包围盒为空。
- [ ] **A7 pin 尺寸提示实测有结论**：记录「尺寸提示是否被采纳」的实测结果与对应降级后的文案；`isRequestPinAppWidgetSupported()` 为假时有降级路径。
- [ ] **A8 预设落到新实例**：从应用内添加 → 配置页预填预设 → 保存后桌面实例的样式/表现与预设一致；待消费槽位一次性、不污染后续实例。
- [ ] **A9 入口与顶栏**：首页顶栏紧凑化后四个既有控件仍可用（触控目标 ≥40px、可访问性标签保留），新入口在有/无原生能力时的两种表现正确。

## Notes

- 上一轮结论「双栏左卡中缝无法用几何填满」仍然成立：中缝是 `SpaceBetween` 的结构性产物，只能靠**内容**填
  （本任务用「下一节」这一行真信息），或让左卡不再撑满（已在上轮被否）。
- 「预设」这个概念的价值不只是省事：它把「内容组合」从「尺寸动态决定」里解放出来 —— 内容由预设固定，
  尺寸只影响连续缩放，因此既满足产品承诺，又不触碰 D16 的禁令。
